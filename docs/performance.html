Performance & Benchmarks

Real numbers from this repository's own BenchmarkDotNet suite — including a head-to-head against AutoMapper and Mapster. We report what the numbers actually say, including where AutoMapperLite loses.

Methodology

Benchmarks live in AutoMapperLite.Benchmarks and run with BenchmarkDotNet v0.15.8 in Release configuration. Eight scenarios — simple object, medium object (8 properties), nested object, deeply nested object (4 levels), custom member mapping, a 100-item collection, a 5,000-item collection, and cold start (first-ever mapping call, including configuration) — are each run against hand-written manual mapping, AutoMapperLite 4.3.0, AutoMapper 16.2.0, and Mapster 10.0.12, all configured equivalently for the same source/destination shapes — with one shared mapper instance per library, reused across calls, never rebuilt inside a hot loop — and asserted to produce identical output before any timing number is trusted (AutoMapperLite.Benchmarks/Verify.cs, run via --verify). 

dotnet run --project AutoMapperLite.Benchmarks -c Release -- --verify
dotnet run --project AutoMapperLite.Benchmarks -c Release -- --filter "*"

Environment: BenchmarkDotNet v0.15.8, Windows 11, Intel Core Ultra 7 255U (14 logical/12 physical cores), 16 GB RAM, .NET SDK 10.0.400, running on .NET 8.0.30 (X64 RyuJIT). The mean-time numbers below (4.3.0 column) were captured with BenchmarkDotNet's --job short preset (3 iterations instead of the usual 15+) because another, unrelated service was running on the same machine at the time and its periodic activity was adding enough timing noise to prevent the default job from converging (BenchmarkDotNet's own precision-checking engine kept extending the run indefinitely, and twice caused a child benchmark process to abort outright). Short-job means carry wider confidence intervals than a full run — treat their relative ordering as reliable but their absolute values as approximate; re-running dotnet run -c Release -- --filter "*" (no --job flag) on a quiet machine will produce tighter numbers. The allocation figures are unaffected by any of this — they come directly from what the compiled code does, not wall-clock timing, and are exact regardless of job preset or system load.

Note on the Nested/DeepNested AutoMapperLite configuration: for the Level1…Level4 chain, the destination property is named Child on every level, matching the source, and each level's type pair has its own registered CreateMap — that's exactly the case AutoMapperLite's own same-name auto-map resolves automatically at plan-compile time (see Why), so no ForMember is registered for it, matching how the AutoMapper and Mapster configurations below rely on their own convention engines for the same chain rather than an explicit per-level mapping. An earlier version of this benchmark routed AutoMapperLite's Child assignments through ForMember calling back into mapper.Map<T>(object) instead — that forced every nested level through the slower untyped dispatch path (entry-point cache lookup, GetType(), boxing) for no reason, and was quietly inflating the DeepNested numbers by roughly 13% versus what AutoMapperLite actually does when configured the way its own docs recommend. The Organization/Country case genuinely needs ForMember in all three libraries' configs, since the destination property (CountryViewModel) is named differently from the source (Country) — same-name auto-map can't apply there regardless of library.

Warm, repeated mapping: manual vs. AutoMapperLite vs. AutoMapper vs. Mapster

AutoMapperLite is not the fastest option on repeated, already-configured calls, but it beats AutoMapper on four of six object-mapping scenarios below, and — as of 4.3.0 — its allocations for every single-object scenario now match hand-written Manual mapping exactly, and its collection allocations are within a few percent of Manual/Mapster's at any size (previously 3.4x higher, regardless of collection size). Mapster remains faster on raw per-call time everywhere in this table. If raw per-call throughput in a hot loop is your primary concern, Mapster will usually win — see Comparison for when each tool makes sense. Rows marked "object API / generic API" show both IMapper.Map<TDestination>(object) (dispatches by the source's runtime type) and IMapper.Map<TSource,TDestination>(TSource) (dispatches by the compile-time type, skipping runtime type resolution entirely) — prefer the generic form in any hot loop where the source type is statically known, since it's now consistently the faster of the two (see Why).

Using the generic API (the recommended shape when the source type is known), AutoMapperLite now beats AutoMapper on every one of the five object-mapping scenarios above — Simple (~2.4x), Medium (~2.2x), Nested (~1.3x), Deeply-nested (~1.3x), and Custom (~2.5x). This is a change from earlier releases, where Nested and Deeply-nested still trailed AutoMapper: those scenarios only had object-API numbers before, and the object-API numbers for AutoMapperLite alone carry the entry-point-cache/GetType() overhead the generic API is specifically designed to skip (see Why). Collection mapping remains the one place AutoMapperLite trails AutoMapper on time (~15% slower at 100 items, ~6% slower at 5,000 items in this run — both within this session's short-job noise margin, effectively a near-tie; was ~6.1x slower before the 4.2.0 release and ~2.5x before the 4.3.0 allocation fix below), while its allocation is now within a few percent of Manual/Mapster's at any size, down from 3.4x — see Why for the specific, measured cause.

AutoMapperLite's own history

4.1.0 replaced the interpreted-reflection mapping engine (used from 3.0.3 through 4.0.2) with one that compiles each type pair into a cached delegate via System.Linq.Expressions. 4.2.0 then redesigned the dispatch layer sitting on top of that compiled work — how a call finds the right compiled delegate in the first place — see Why below for both. Why AutoMapperLite is faster than it used to be, and where it still loses

Every source/destination type pair is compiled once, lazily, into a real Func<TSource, TDestination> via System.Linq.Expressions (Core/MappingPlanCompiler.cs), cached on the owning MapBuilder instance — this was the 4.1.0 redesign, and it replaced, on the hot path: PropertyInfo.GetValue/SetValue for every property, MethodInfo.Invoke for every internal dispatch, and Activator.CreateInstance for every destination object.

That compiled work, though, still had to be found on every call, and 4.2.0's fix is entirely in that dispatch layer, not the compiled per-property work itself. Before 4.2.0, the untyped Map<TDestination>(object) entry point re-resolved config.GetMap<TSource,TDestination>() — a dictionary lookup — on every single call, in addition to the cache lookup that found the dispatch wrapper in the first place: two dictionary lookups per map instead of one. 4.2.0 caches the dispatch per Mapper instance instead of globally, letting it resolve the builder once and reuse it directly — this alone is most of the ~38% improvement on the Simple/Medium/Custom scenarios above, and it's also why AutoMapperLite now beats AutoMapper on those three.

For collections, the fix is more dramatic: pre-4.2.0, mapping a List<TSource> to a List<TDestination> called item.GetType() and re-resolved the entry point for every element. 4.2.0 determines the source collection's item type once — from List<T>'s generic argument, an array's element type, or whichever IEnumerable<T> it implements — and runs a strongly-typed foreach loop with zero per-item type lookup and zero boxing of value-typed items. The remaining time gap to AutoMapper on collections is the outer dispatch cost inherent to the untyped object-based public API — AutoMapper pays something similar; Mapster's typical usage pattern (source.Adapt<T>(), an extension method generic on the caller's own static type) sidesteps runtime type resolution at the call site entirely, which is a structural difference, not a missed optimization.

4.3.0 found and fixed a much larger, and entirely separate, problem: a per-call allocation hiding inside what looked like ordinary lazy initialization. The method that hands out a builder's compiled delegate was written as LazyInitializer.EnsureInitialized(ref _compiledMap, () => MappingPlanCompiler.Compile(this, config)) directly in its body. That lambda captures this and config, so C# must allocate a new closure object and a new delegate wrapping it at the call site every time that line runs — whether or not EnsureInitialized ends up calling it. Since this method is called on every collection element, and on every same-name nested single-object property assignment (once per parent object mapped), that throwaway allocation was happening continuously on the warm path, not just once at startup. Rewriting it to check the field directly first, and only reach the lambda-allocating code once, ever, per builder, is what closed the allocation gap shown throughout this page: Simple/Medium/Nested/DeepNested object mapping now allocate exactly what Manual mapping does, and collection allocation at any size is now within a few percent of Manual/Mapster's, down from 3.4x. It also explains a chunk of this release's time improvement, since less garbage means less time spent in the GC.

For callers who do know the source type at compile time, IMapper.Map<TSource, TDestination>(TSource source) (added in 4.2.0) skips source.GetType() and return-value boxing entirely. Measuring it directly during 4.3.0's work turned up a second, related finding: its original implementation was actually slower than the untyped overload it was designed to beat, because each call still went through an uncached IMapperConfig.GetMap<,>() lookup plus the same closure-allocation cost described above — costs the untyped overload's own cached dispatch closure had already eliminated for itself. 4.3.0 gives the generic overload the identical per-Mapper-instance cached-closure treatment, and it's now consistently the faster of the two API shapes (see the object-API/generic-API columns above). Nested same-name auto-mapped properties get the equivalent treatment for free: 4.2.0 resolves the nested MapBuilder once, at plan-compile time (not per call), and bakes the actual builder reference into the compiled expression as a constant, so the compiled parent delegate calls straight into the nested builder's own compiled delegate with no runtime type resolution at all.

ForPath nested-path mapping is deliberately left interpreted rather than compiled: profiling showed it wasn't a bottleneck relative to plain auto-mapped properties, and correctly compiling arbitrary-depth, dynamically-walked destination paths (with per-segment custom mapping functions) is exactly the kind of complexity not worth taking on for a cold path. See CLAUDE.md in the repository for the full technical breakdown, including why both the compiled plan and the 4.2.0 dispatch caches are scoped per-instance rather than shared globally.
