Performance & Benchmarks

Real numbers from this repository's own BenchmarkDotNet suite — not marketing claims.

Methodology

Benchmarks live in AutoMapperLite.Benchmarks and run with BenchmarkDotNet in Release configuration. The numbers below compare AutoMapperLite 3.0.1 (before the mapping-hot-path optimization work) against 3.0.3 (after it); 4.0.1 carries the same mapping engine forward unchanged. 

dotnet run --project AutoMapperLite.Benchmarks -c Release

Environment: BenchmarkDotNet v0.14.0, Windows 11, .NET 8.0.30, X64 RyuJIT AVX2.

Why it got faster

The mapping engine is still reflection-based (no runtime IL/expression compilation), but it now caches what used to be re-resolved on every single call:

  • MakeGenericMethod/GetMethod results for the internal mapping methods, cached per type pair — previously re-run once per collection item.
  • Type.GetProperties() results, cached per type.
  • Source-property-by-name lookups, cached per type as a dictionary instead of a linear GetProperty(name) reflection call.
  • Nested ForPath key groupings, computed once per MapBuilder instead of re-scanned with LINQ on every mapped object.

See CLAUDE.md in the repository for the full technical breakdown.

An honest note on comparisons

We have not benchmarked AutoMapperLite head-to-head against AutoMapper or Mapster, and we won't publish speed claims about those projects without real, reproducible numbers. If raw peak throughput for large or complex mapping graphs is your primary concern, benchmark your actual workload against the alternatives directly — see the comparison page for a feature-level (not performance) comparison.
