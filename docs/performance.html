Performance & Benchmarks

Real numbers from this repository's own BenchmarkDotNet suite — including a head-to-head against AutoMapper and Mapster. We report what the numbers actually say, including where AutoMapperLite loses.

Methodology

Benchmarks live in AutoMapperLite.Benchmarks and run with BenchmarkDotNet v0.15.8 in Release configuration. Three scenarios (map a simple object, map a nested object, map a 100-item collection) are each run four ways: hand-written manual mapping, AutoMapperLite 4.0.2, AutoMapper 16.2.0, and Mapster 10.0.12, all configured equivalently for the same source/destination shapes. 

dotnet run --project AutoMapperLite.Benchmarks -c Release --filter "*"

Environment: BenchmarkDotNet v0.15.8, Windows 11, Intel Core Ultra 7 255U, .NET SDK 10.0.400, running on .NET 8.0.30 (X64 RyuJIT).

AutoMapperLite vs. manual mapping vs. AutoMapper vs. Mapster

AutoMapperLite is not the fastest option here. AutoMapper and Mapster both compile expression trees into delegates at configuration time, which is fundamentally faster than AutoMapperLite's cached-reflection approach. If raw throughput in a hot path is your primary concern, AutoMapper or Mapster will outperform AutoMapperLite — see Comparison for when each tool makes sense.

In absolute terms, AutoMapperLite is still sub-microsecond for single-object mapping and allocates only 2–2.75x more than the fastest option, not an order of magnitude more — but for collection mapping the gap widens (roughly 21x slower than AutoMapper, 33x slower than Mapster for 100 items), because AutoMapperLite pays a reflection-driven per-property cost for every single element, while compiled-expression mappers pay it once at configuration time.

Why AutoMapperLite is faster than it used to be, and why it's still not the fastest

The mapping engine is still reflection-based (no runtime IL/expression compilation), but it now caches what used to be re-resolved on every single call:

  • MakeGenericMethod/GetMethod results for the internal mapping methods, cached per type pair — previously re-run once per collection item.
  • Type.GetProperties() results, cached per type.
  • Source-property-by-name lookups, cached per type as a dictionary instead of a linear GetProperty(name) reflection call.
  • Nested ForPath key groupings, computed once per MapBuilder instead of re-scanned with LINQ on every mapped object.

What it deliberately does not do is compile expression trees or generate IL at configuration time — that's the single biggest reason AutoMapper and Mapster are faster above. Adding that would be a substantial architectural change in exchange for the one thing AutoMapperLite currently isn't: the fastest option. See CLAUDE.md in the repository for the full technical breakdown.
