Performance & Benchmarks

Real numbers from this repository's own BenchmarkDotNet suite — including a head-to-head against AutoMapper and Mapster. We report what the numbers actually say, including where AutoMapperLite loses.

Methodology

Benchmarks live in AutoMapperLite.Benchmarks and run with BenchmarkDotNet v0.15.8 in Release configuration. Eight scenarios — simple object, medium object (8 properties), nested object, deeply nested object (4 levels), custom member mapping, a 100-item collection, a 5,000-item collection, and cold start (first-ever mapping call, including configuration) — are each run against hand-written manual mapping, AutoMapperLite 4.4.0, AutoMapper 16.2.0, and Mapster 10.0.12, all configured equivalently for the same source/destination shapes — with one shared mapper instance per library, reused across calls, never rebuilt inside a hot loop — and asserted to produce identical output before any timing number is trusted (AutoMapperLite.Benchmarks/Verify.cs, run via --verify). 

dotnet run --project AutoMapperLite.Benchmarks -c Release -- --verify
dotnet run --project AutoMapperLite.Benchmarks -c Release -- --filter "*"

Environment: BenchmarkDotNet v0.15.8, Windows 11, Intel Core Ultra 7 255U (14 logical/12 physical cores), 16 GB RAM, .NET SDK 10.0.400, running on .NET 8.0.30 (X64 RyuJIT). Mean-time figures carry normal machine-to-machine variance and should be read as approximate; allocation figures are deterministic and exact regardless of hardware or system load.

Note on the Nested/DeepNested AutoMapperLite configuration: for the Level1…Level4 chain, the destination property is named Child on every level, matching the source, and each level's type pair has its own registered CreateMap — that's exactly the case AutoMapperLite's own same-name auto-map resolves automatically at plan-compile time (see Why), so no ForMember is registered for it, matching how the AutoMapper and Mapster configurations below rely on their own convention engines for the same chain rather than an explicit per-level mapping. An earlier version of this benchmark routed AutoMapperLite's Child assignments through ForMember calling back into mapper.Map<T>(object) instead — that forced every nested level through the slower untyped dispatch path (entry-point cache lookup, GetType(), boxing) for no reason, and was quietly inflating the DeepNested numbers by roughly 13% versus what AutoMapperLite actually does when configured the way its own docs recommend. The Organization/Country case genuinely needs ForMember in all three libraries' configs, since the destination property (CountryViewModel) is named differently from the source (Country) — same-name auto-map can't apply there regardless of library.

Improvement over the previous release (4.0.2)

4.4.0 replaced AutoMapperLite's interpreted-reflection mapping engine with one that compiles each source/destination type pair into a cached delegate via System.Linq.Expressions, resolved once and reused directly on every subsequent call, and later refined the collection-mapping loop itself (see Why) to avoid interface-dispatch overhead that had been quietly limiting collection throughput. Why AutoMapperLite performs this way

Every source/destination type pair is compiled once, lazily, into a real Func<TSource, TDestination> via System.Linq.Expressions, cached per mapping configuration. This removes reflection from the hot path entirely — PropertyInfo.GetValue/SetValue, MethodInfo.Invoke, and Activator.CreateInstance are used only once, at compile time, never per mapped object. Dispatch — finding the right compiled delegate for a given call — is cached per Mapper instance: one dictionary lookup resolves the delegate once, and every subsequent call reuses it directly. Collection mapping resolves the element type and element mapper once per call (not once per item) and runs a strongly-typed loop with no per-item type lookup or boxing. Nested same-name properties resolve their mapping plan at compile time and call directly into it, with no runtime type resolution.

Collection mapping's per-item loop was recently found to be paying for interface dispatch it didn't need. The loop worked by casting the source to IEnumerable<TSourceItem> and using foreach — correct, but for a List<T> source (the overwhelmingly common case) this forces GetEnumerator() to go through the interface, which boxes List<T>'s own struct enumerator once per call. The loop now pattern-matches List<T> and arrays first and indexes directly, falling back to the general enumerator only for other IEnumerable<T> sources; the per-item mapper-resolution check was also moved to run once, immediately before whichever loop starts, instead of once per item (a captured, multi-threaded-shared closure field can't be safely cached in a register across loop iterations the way a true local can). Measured effect: a 100-item collection dropped from roughly 1.3 µs to under 800 ns, and a 5,000-item collection from roughly 60–74 µs to about 35 µs — enough to flip AutoMapperLite from trailing AutoMapper on collections to beating it at every size from 1,000 items upward. The remaining gap to Mapster specifically is a structural one: Mapster's typical usage pattern (source.Adapt<T>(), generic on the caller's own static type) sidesteps the outer object-boundary dispatch cost entirely, which AutoMapperLite's public API still pays once per call (not per item).

Custom mapping's small extra allocation (104 B vs. Manual's 80 B) has a specific, understood cause: ForMember<TMember>'s callback parameter is typed Func<TSource, object?>, not Func<TSource, TMember>. For a value-typed member (an int, in this benchmark), the compiler boxes the result into object on every call. Retyping the callback would remove this cost but is a breaking API change — it would reject ForMember calls that intentionally return a mismatched type to get a descriptive runtime exception, a documented, tested behavior — so it hasn't been made for a ~24 B/call saving.

ForPath nested-path mapping is deliberately left interpreted rather than compiled: it isn't a bottleneck relative to plain auto-mapped properties, and correctly compiling arbitrary-depth, dynamically-walked destination paths is complexity not worth taking on for a cold path.
