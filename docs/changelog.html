Changelog

Release history for AutoMapperLite. Full detail also maintained in CHANGELOG.md.

4.3.0 current release — 2026-09-03

  • Fixed a per-call closure allocation — the single largest source of AutoMapperLite's excess allocation versus manual mapping and Mapster. The method every dispatch path uses to reach a compiled mapping delegate wrote LazyInitializer.EnsureInitialized(ref _compiledMap, () => MappingPlanCompiler.Compile(this, config)) directly in its body. That lambda captures this and config, so C# allocates a new closure object and delegate wrapping it at the call site on every single call, whether or not the factory is ever invoked. This hit every same-name nested single-object property (once per parent object mapped) and the typed Map<TSource,TDestination> overload directly. Fixed by checking the field directly first and only falling through to the lambda-allocating path once, ever, per builder. See Performance for full numbers and methodology:
    • Simple/Medium/Nested/Deeply-nested object mapping now allocate exactly what Manual mapping does (32 B/80 B/80 B/248 B), down from 128 B/176 B/272 B/632 B
    • 100-item collection: 13.44 KB → 4.06 KB allocated (was 3.4x Manual's/Mapster's 3.96 KB, now within 3%)
    • 5,000-item collection: 664.25 KB → 195.48 KB allocated (was 3.4x Manual's/Mapster's 195.37 KB, now within 0.06%)
    • Verified this holds at scale: at 100,000 items, allocation is within 0.007% of Manual's (previously ~3.4x at any size), and time is within 11% of Manual's — actually beating AutoMapper by ~18% at that size
  • Fixed IMapper.Map<TSource, TDestination>(TSource) (added in 4.2.0) being measurably slower than the untyped overload it was designed to beat. Each call still went through an uncached IMapperConfig.GetMap<,>() lookup plus the closure allocation above, while the untyped overload's own cached dispatch closure had already eliminated both. Added a dedicated per-Mapper-instance cache mirroring the untyped path's own, so the typed overload now has the identical shape — one dictionary lookup keyed by compile-time Type, then a direct delegate invocation — and is consistently the faster of the two API shapes.
  • Added a regression test guarding a further optimization that was considered and deliberately not made: eagerly resolving a nested property's compiled delegate at the parent's plan-compile time would StackOverflow on self-referential types (e.g. Employee.Manager: Employee) even with fully acyclic data. Documented as a permanent constraint in CLAUDE.md.
  • No public API or behavior changes since 4.2.0 — dispatch-layer allocation/performance work only, verified against the full test suite (120 tests) and the --verify cross-library output-equality harness.

4.2.0 — 2026-08-29 deprecated

  • Dispatch-layer performance redesign. 4.1.0 compiled each mapping into an expression-tree delegate but still paid avoidable runtime-dispatch costs on top of that: the untyped Map<TDestination>(object) entry point re-resolved the destination config on every single call (two dictionary lookups per map), collection items were dispatched via GetType() plus a dictionary lookup per element, and nested same-name auto-mapped properties routed through that same per-call dispatch despite the nested type pair being known at plan-compile time. 4.2.0 fixes all three — see Performance for full numbers and methodology:
    • Simple object: 67.6 ns → 42.2 ns (~38% faster, now faster than AutoMapper's 58.2 ns)
    • 100-item collection: 6,986.7 ns → 2,744.1 ns (~61% faster)
    • 5,000-item collection: 390.81 µs → 156.47 µs (~60% faster)
    • Cold start improved further: 281.7 µs → 201.6 µs, still the fastest of the three libraries compared
  • Added: IMapper.Map<TSource, TDestination>(TSource source) — a strongly-typed overload for call sites where the source type is known at compile time; skips source.GetType(), the entry-point cache, and return-value boxing entirely. Additive for callers; technically breaking for anyone implementing IMapper themselves.
  • Disclosed behavior change: List<T> destination mapping now resolves the item map from the source collection's declared item type, not each element's runtime type — a List<Base> containing Derived instances now maps every element through Base's registered map instead of dispatching per element (which previously threw for a Derived element unless it had its own separately-registered map).
  • No public API breaking changes for callers since 3.0.3.

4.1.0 — 2026-08-29 deprecated

  • Performance redesign: each source/destination type pair is now compiled into a cached Func<TSource, TDestination> via System.Linq.Expressions on first use, instead of being interpreted through PropertyInfo.GetValue/SetValue, MethodInfo.Invoke, and Activator.CreateInstance on every call. Measured on this repo's own BenchmarkDotNet suite (full numbers and methodology on Performance):
    • Simple object: 242.0 ns → 67.6 ns (~3.6x faster)
    • Nested object: 424.1 ns → 137.8 ns (~3.1x faster)
    • 100-item collection: 26,009.1 ns → 6,986.7 ns (~3.7x faster)
    • Cold start (first mapping call, including compilation) is now faster than both AutoMapper's and Mapster's own cold start
  • AutoMapperLite is still slower than AutoMapper and Mapster on warm, repeated auto-mapped calls, especially collections — see Comparison for the honest breakdown of where each library wins.
  • Disclosed behavior change (not a breaking API change): exceptions raised during mapping now propagate directly as InvalidOperationException instead of being wrapped in System.Reflection.TargetInvocationException — that wrapping was an implementation detail of the old reflection dispatch, never part of the documented contract.
  • ForPath nested-path mapping is unchanged (still interpreted) — profiling showed it wasn't a hot path.
  • No public API breaking changes since 3.0.3.

4.0.2 — 2026-08-29 deprecated

  • Fixed: updated test tooling (xunit.v3, Microsoft.NET.Test.Sdk 18.9.0) only supports net8.0+ — AutoMapperLite.Tests now targets net8.0/net9.0/net10.0 (the library itself is unaffected and still targets net6.0-net10.0)
  • Fixed: a Microsoft Testing Platform v2 change dropped dotnet test's legacy VSTest bridge on the .NET 10 SDK — a repo-root global.json now opts into native MTP mode
  • Fixed: Activator.CreateInstance failures (e.g. mapping to a positional record with no parameterless constructor) now throw a clear InvalidOperationException naming the type, instead of a bare MissingMethodException
  • Added real, measured BenchmarkDotNet comparisons against manual mapping, AutoMapper 16.2.0, and Mapster 10.0.12 — see Performance. AutoMapperLite is not the fastest of the four; docs and package description no longer implied otherwise
  • Verified and documented previously-untested behaviors: null source properties are skipped (not assigned), auto-map requires an exact type match, and records with a parameterless constructor + init-only properties map correctly
  • All NuGet packages kept at their latest versions — none downgraded

4.0.1 — 2026-08-29

Official rebrand and release. All versions prior to 4.0.1 are deprecated.

  • Official project website: automapperlite.atkhssn.info
  • New visual identity: icon, favicons, app icons, social preview images, light/dark logo lockups
  • Full XML documentation comments on the public API (IntelliSense support)
  • NuGet package metadata overhauled: accurate description, project URL, refined tags
  • Static documentation site expanded: Getting Started, Guide, Performance, Comparison, FAQ, SEO/AEO metadata, structured data
  • Carries forward every 3.0.x fix below — no public API breaking changes since 3.0.3

3.0.3 — 2026-08-29 deprecated

  • Multi-targets net6.0/net7.0/net8.0/net9.0/net10.0 (previously net8.0 only)
  • Fixed: mapping to a value-type (struct) destination silently produced an unpopulated struct
  • Fixed: a List<T> destination property was never auto-mapped even when a map was registered for the item types
  • Hardened MapperConfig and DI registration for concurrent use
  • Reduced mapping-hot-path allocations and reflection overhead (~3.3-4x faster, ~6.5-8x less allocation)
  • Clearer exception when a ForMember/ForPath function returns an incompatible value
  • Fixed dotnet pack failing on a clean multi-targeted tree

3.0.2 deprecated

  • Fixed: multiple ForPath calls under the same top-level destination property now all apply, instead of only the first

3.0.1 deprecated

  • Added ForPath and ForMember support
  • Improved collection mapping (List<T>)
  • Simplified usage with Map<TDestination>(TSource) format
  • Support for nested property mapping and configuration profiles
