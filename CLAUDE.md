# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AutoMapperLite is a lightweight object-to-object mapper for .NET (a small AutoMapper alternative), published as an MIT-licensed NuGet library. The repo also contains an xUnit test project, a BenchmarkDotNet benchmark project (which also benchmarks AutoMapper and Mapster for comparison — dev-only dependencies, not shipped), and a static HTML documentation site (`docs/`) alongside the library.

**The mapping engine compiles a real delegate per (source, destination) type pair via `System.Linq.Expressions`, once, lazily, on first use** — it is not interpreted reflection on every call. This is a deliberate architectural choice made after profiling showed reflection (`PropertyInfo.GetValue`/`SetValue`, `MethodInfo.Invoke`) was 7–8x slower than the equivalent compiled/direct code (see `docs/performance.html` for the measured numbers, and the "Architecture" section below for what's compiled vs. what's deliberately still interpreted).

`docs/` is a hand-written, dependency-free static site (`index.html`, `api-reference.html`, `examples.html`, `assets/`) — no build step, no generator. Every code sample in `docs/examples.html` was executed and asserted against the real library before being written down (not just read for plausibility), because the README previously shipped a flagship example that looked reasonable but threw `InvalidOperationException` at runtime — see the `ForMember`/`ForPath` note further down. If you edit an example in `docs/`, re-run it (a throwaway console project referencing `AutoMapperLite.csproj` is enough) before trusting it. `docs/` is not currently deployed anywhere (no GitHub Pages / CI wired up) — it's meant to be opened locally or published later by enabling GitHub Pages against `/docs`.

## Commands

```bash
# Build everything (library, tests, benchmarks)
dotnet build AutoMapperLite.slnx

# Pack the NuGet package — must be `dotnet pack`, not `dotnet build`.
# GeneratePackageOnBuild is deliberately NOT set: with a multi-targeted
# project it triggers a known MSBuild/NuGet ordering bug (NU5026 — "file to
# be packed was not found on disk") when `dotnet pack` is later run directly
# on a clean tree. Plain `dotnet build` no longer produces a .nupkg.
dotnet pack AutoMapperLite.csproj -c Release

# Run the test suite (all TFMs the test project targets)
dotnet test AutoMapperLite.Tests/AutoMapperLite.Tests.csproj

# Run a single test
dotnet test AutoMapperLite.Tests/AutoMapperLite.Tests.csproj --filter "FullyQualifiedName~MapperTests.Map_UsesForMember_ForCustomMapping"

# Run benchmarks (Release build required by BenchmarkDotNet)
dotnet run --project AutoMapperLite.Benchmarks -c Release

# Run the test suite against a specific target framework
dotnet test AutoMapperLite.Tests/AutoMapperLite.Tests.csproj -f net8.0
```

Note: `AutoMapperLite.csproj` explicitly excludes the `AutoMapperLite.Tests/` and `AutoMapperLite.Benchmarks/` folders from its own compile globs (see the `Compile Remove` items) since those projects live as subdirectories of the main project's folder — keep those excludes in sync if the project layout changes.

**Test tooling is xunit.v3 (Microsoft Testing Platform / MTP), not classic xunit 2.x/VSTest.** Two consequences, both load-bearing:
- **Test-executable TFMs are net8.0/net9.0/net10.0 only** — `AutoMapperLite.Tests.csproj` intentionally does *not* include net6.0/net7.0, because `xunit.v3` 4.0.0 and `Microsoft.NET.Test.Sdk` 18.9.0 only support `net472+`/`net8.0+` (stated directly in `xunit.v3`'s own package description). The *library* (`AutoMapperLite.csproj`) still multi-targets `net6.0;net7.0;net8.0;net9.0;net10.0` and is compile-verified on all five — this is a test-tooling floor, not a library constraint. Do not re-add net6.0/net7.0 to the test project without downgrading the test packages (which defeats the point of keeping them current).
- **`dotnet test` requires the repo-root `global.json`** (`{"test":{"runner":"Microsoft.Testing.Platform"}}`). xunit.v3 here is built on MTP v2 (`xunit.v3.mtp-v2`), which drops the legacy VSTest-bridge `dotnet test` path entirely on the .NET 10 SDK — without `global.json`, `dotnet test` hard-errors with "Testing with VSTest target is no longer supported...". Don't remove `global.json` or add `TestingPlatformDotnetTestSupport` (the old bridge property) back; neither restores VSTest-mode compatibility with MTP v2 on SDK 10+, only native MTP mode works. See https://aka.ms/dotnet-test-mtp-error for Microsoft's own migration notes.

The benchmark project stays single-targeted (net8.0); it's a dev-only tool, not shipped.

## Architecture

The library has a small, fixed pipeline: **Profile → MapperConfig → MapBuilder → (compiled plan) → Mapper**.

- `Interfaces/IMapper.cs`, `Interfaces/IMapperConfig.cs` — public contracts.
- `Core/MapperConfig.cs` — holds all registered mappings in a `ConcurrentDictionary<(Type source, Type dest), object>` keyed by the (source, destination) type pair (thread-safe so a `CreateMap` call can't corrupt state if it ever races with `GetMap`/`HasMap` reads against an already-published singleton config). `CreateMap<TSource, TDestination>()` registers a new `MapBuilder<TSource, TDestination>`; `GetMap<TSource, TDestination>()` retrieves it (throws if missing); `HasMap` checks existence for a given type pair — used by the plan compiler to decide whether a mismatched-type property can be recursively mapped.
- `Mapping/MapBuilder.cs` — fluent builder returned by `CreateMap`. `ForMember(dest => dest.X, src => ...)` and `ForPath(dest => dest.A.B.C, src => ...)` both resolve the destination expression into a dot-delimited string key (e.g. `"A.B.C"`) via `GetMemberPath`, and store a `Func<TSource, object?>` against that key in `MemberMappings`. `ForPath` is currently just an alias for `ForMember` — the "path" behavior comes entirely from how the compiled plan interprets keys containing dots. `GetNestedKeys(topLevelProperty)` returns every registered key nested under a top-level property name, grouped once via a `Lazy<Dictionary<string, List<string>>>` (safe because `MemberMappings` is only ever written during `Profile.Configure()`, before any mapping runs). **`MapBuilder` also owns the compiled plan itself**: a `Func<TSource, TDestination>? _compiledMap` field, built lazily via `LazyInitializer.EnsureInitialized` the first time `Map(source, config)` is called on that specific builder instance — see "Why the plan lives on `MapBuilder`, not a global cache" below.
- `Mapping/Profile.cs` — abstract base class users subclass; `Configure(IMapperConfig)` is where `CreateMap` calls go.
- `Core/MappingPlanCompiler.cs` — builds the actual `Expression<Func<TSource, TDestination>>` for a given builder and compiles it (`.Compile()`) into a real delegate. For each writable destination property, in the same priority order as before: (1) an exact `MemberMappings` match compiles to `Expression.Invoke` on the captured user delegate + a call to `Mapper.ConvertMappedValue<TMember>` (a generic helper, resolved once via `Expression.Call` on a closed `MethodInfo` — a direct compiled call, not a reflection `Invoke`) for the descriptive-exception behavior; (2) a nested `ForPath` match compiles to a direct call into `Mapper.ApplyNestedMapping<TSource,TDestination>` (see below — deliberately still interpreted internally, but *dispatched into* via a compiled call); (3) same-name/same-type auto-map compiles to a **direct property assignment** (`Expression.Assign(Expression.Property(...), Expression.Property(...))`), wrapped in a null-check for reference/nullable types so a `null` source value is skipped rather than overwriting the destination's own default; (4) same-name/mismatched-type auto-map (including matching `List<T>` item types) compiles to a direct call into `Mapper.MapCore<TDestination>` for the recursive conversion, only if `config.HasMap(...)` was true *at plan-build time* — this is safe because `MemberMappings`/registered maps are documented-immutable after `Profile.Configure()` finishes, before any mapping runs. Destination instances are built via `Expression.New(type)`, **not** `type.GetConstructor(Type.EmptyTypes)` — the latter returns `null` for value types without an explicitly-declared parameterless constructor (a real reflection gotcha that broke struct destinations during this redesign; `Expression.New(Type)` handles value types correctly on its own and only throws for reference types genuinely missing a parameterless ctor).
- `Core/Mapper.cs` — the runtime-type-dispatch layer for the untyped `Map<TDestination>(object? source)` API, and the home of the new strongly-typed `Map<TSource, TDestination>(TSource source)` overload. As of the 4.2.0 dispatch redesign, its caches are **per-`Mapper`-instance**, not global/static (see "Why the dispatch caches moved from static to per-instance" below):
  - `Map<TDestination>(object? source)` handles the `null`-source case, then either routes to `MapList` (for `List<T>` destinations) or resolves an entry point via `GetOrBuildEntryPoint(source.GetType(), typeof(TDestination))` and invokes it directly.
  - `Map<TSource, TDestination>(TSource source)` — added in 4.2.0, given its own per-instance cache (`_typedEntryPoints`) in 4.3.0. Both types are known at the call site, so it skips `source.GetType()` and the return-value boxing the untyped overload needs, dispatching by the *compile-time* type `TSource` (not `source`'s runtime type) — the one observable difference from the untyped overload. **4.2.0's original implementation** (`_config.GetMap<TSource, TDestination>().Map(source, _config)` on every call) measured *slower* than the untyped overload despite being designed to beat it: `IMapperConfig.GetMap<,>()` is its own uncached-at-the-Mapper-level dictionary lookup, and `MapBuilder.Map` at the time additionally allocated a closure on every call (see `GetCompiledMap` below) — two costs the untyped overload's cached closure doesn't pay, since it captures an already-resolved compiled delegate directly. `_typedEntryPoints` (built via `BuildTypedEntryPoint<TSource,TDestination>`, mirroring `BuildEntryPoint`/`_entryPoints` below exactly except it stores/returns a boxed `Delegate` instead of wrapping it in an `object`-parameter closure) gives it the identical shape: one dictionary lookup keyed by `typeof(TSource)`/`typeof(TDestination)`, then a direct invocation.
  - `GetOrBuildEntryPoint(Type, Type)` caches a `Func<object, object?>` per type pair in an **instance-level** `ConcurrentDictionary` (`_entryPoints`). The closure resolves `config.GetMap<TSource,TDestination>()` **once**, when the entry is first built (via `MakeGenericMethod` + a single reflective `Invoke`, never in the hot path), and captures the already-*compiled delegate itself* (via `MapBuilder.GetCompiledMap`, not the builder) — every subsequent call for that pair goes straight from the dictionary lookup to a direct delegate invocation, no further indirection. The pre-4.2.0 design cached a config-agnostic wrapper *globally* that re-resolved `config.GetMap<,>()` — itself a dictionary lookup — on *every single invocation*, so every `Map` call paid for two dictionary lookups instead of one; this was the single largest fixed per-call cost in the whole pipeline at the time.
  - `MapList(object, Type)` / `TryGetDeclaredItemType` / `GetOrBuildListMapper` / `BuildListMapper<TSourceItem,TDestItem>` — the `List<T>`-destination path. `TryGetDeclaredItemType` inspects the *source collection's own* `Type` once (via `List<T>`'s generic argument, an array's element type, or the first `IEnumerable<T>` it implements) to find the item type without looking at any element. When that succeeds (the overwhelming common case — `List<T>`, arrays, LINQ iterators), `BuildListMapper<TSourceItem,TDestItem>` builds a **strongly-typed loop, cached per (Mapper instance, item type pair)**, that does a real `foreach (TSourceItem item in source)` with zero per-item `GetType()`, zero per-item dictionary lookup, and zero boxing of value-typed items. The item builder itself is resolved lazily inside that loop (`builder ??= config.GetMap<,>()`, a deliberately benign, lock-free race — see the comment on `BuildListMapper`) so an empty collection never requires a registered map. `MapListByRuntimeType` is the fallback for source collections whose item type can't be determined up front (non-generic `IEnumerable`/`ArrayList`): it dispatches per item by that item's *runtime* type, same as the pre-4.2.0 implementation, but with a one-slot "monomorphic inline cache" so consecutive same-typed items reuse the last resolved entry point instead of re-querying the dictionary.
  - `PublicPropertiesCache`/`PropertiesByNameCache` — still-cached reflection metadata, `static` (process-wide, by design — see the constraints list below), consulted only at plan-*build* time (once per type pair), not per mapped object.
  - `ApplyNestedMapping<TSource, TDestination>` — **deliberately still interpreted** (a runtime `PropertyInfo` walk), not compiled. ForPath targets are typically rare relative to plain auto-mapped properties, and compiling the dynamic, arbitrary-depth segment-walking + prefix-registered-intermediate-mapping logic correctly would be significant added complexity for a cold path with zero benchmark coverage. The *dispatch into* this method from the compiled plan is still a direct compiled call (fast); only the walk itself remains interpreted. If you're tempted to compile this too, get a benchmark showing it matters first.
  - `CreateInstance(Type)` — still used for `List<T>` instantiation on the `MapListByRuntimeType` fallback path (always has a parameterless ctor, essentially never throws) and by `ApplyNestedMapping`'s intermediate objects; wraps `Activator.CreateInstance` with the same clear-exception behavior as `MappingPlanCompiler`'s `Expression.New`-based construction.
  - `InvokeBuilder(MethodInfo)` — a small helper both `GetOrBuildEntryPoint` and `GetOrBuildListMapper` route their `MakeGenericMethod(...).Invoke(this, null)` calls through. Because `BuildEntryPoint` now resolves `config.GetMap<,>()` *inside* the reflectively-invoked method (to get the once-only resolution described above), a missing registration throws from inside that `Invoke` call and would otherwise arrive wrapped in a `TargetInvocationException` — `InvokeBuilder` unwraps it via `ExceptionDispatchInfo`, preserving the disclosed "no `TargetInvocationException` wrapping" behavior described below.
- `Core/MappingPlanCompiler.cs` — builds the actual `Expression<Func<TSource, TDestination>>` for a given builder and compiles it (`.Compile()`) into a real delegate. For each writable destination property, in priority order: (1) an exact `MemberMappings` match compiles to `Expression.Invoke` on the captured user delegate + a call to `Mapper.ConvertMappedValue<TMember>` (a generic helper, resolved once via `Expression.Call` on a closed `MethodInfo` — a direct compiled call, not a reflection `Invoke`) for the descriptive-exception behavior; (2) a nested `ForPath` match compiles to a direct call into `Mapper.ApplyNestedMapping<TSource,TDestination>` (see above — deliberately still interpreted internally, but *dispatched into* via a compiled call); (3) same-name/same-type auto-map compiles to a **direct property assignment** (`Expression.Assign(Expression.Property(...), Expression.Property(...))`), wrapped in a null-check for reference/nullable types so a `null` source value is skipped rather than overwriting the destination's own default; (4) same-name/mismatched-type auto-map — both for a single nested object (`BuildNestedObjectAssignment`) and for matching `List<T>` item types (`BuildNestedListAssignment`) — resolves the nested `MapBuilder` (or, for lists, the item-type `MapBuilder`) via `config.GetMap<,>()` **once, here, at plan-compile time**, and bakes the actual builder reference into the compiled expression as an `Expression.Constant`. The compiled parent delegate then calls straight into that already-known nested builder's own compiled delegate — zero runtime type resolution, zero dictionary lookup, zero boxing. (Only if `config.HasMap(...)` was true at plan-build time; this is safe because `MemberMappings`/registered maps are documented-immutable after `Profile.Configure()` finishes, before any mapping runs.) Prior to 4.2.0 this routed through `Mapper.MapCore<TDestination>(object, config)` at runtime instead, which needed the nested value's `GetType()` plus a dictionary lookup on *every single call* despite the exact nested type pair already being known at compile time — this was one of the two biggest fixed per-call costs in the pipeline (the other being the entry-point double-lookup described above), and both were purely dispatch-layer problems, not anything to do with the compiled per-property assignment work itself. Destination instances are built via `Expression.New(type)`, **not** `type.GetConstructor(Type.EmptyTypes)` — the latter returns `null` for value types without an explicitly-declared parameterless constructor (a real reflection gotcha that broke struct destinations during the original compiled-plan redesign; `Expression.New(Type)` handles value types correctly on its own and only throws for reference types genuinely missing a parameterless ctor).
- `Extensions/ServiceCollectionExtensions.cs` — `AddAutoMapperLite(Assembly)` DI entry point: scans the given assembly for concrete `Profile` subclasses with a parameterless constructor, instantiates each and calls `Configure` against a single shared `MapperConfig`, then registers `IMapperConfig` and `IMapper`/`Mapper` **both as singletons** — `Mapper` holds no per-request state beyond the (already-singleton) config and its own dispatch caches, so scoping it would only add allocation for no benefit, and would also mean each scope re-pays every cache-miss cost independently.

### Why the plan lives on `MapBuilder`, not a global cache

The compiled plan captures the *specific* `MapBuilder` instance's `MemberMappings`/nested-path configuration as closures. Two different `IMapperConfig` instances mapping the same `(TSource, TDestination)` pair *differently* (very common in the test suite — many tests create their own `new MapperConfig()` for the same test model types with different `ForMember` setups) must never share a compiled plan. Caching the plan on the `MapBuilder` instance itself (rather than in a global `ConcurrentDictionary<(Type,Type), ...>`) makes this structurally impossible to get wrong: a given `MapBuilder` object is only ever reachable through the one `MapperConfig` that created and owns it.

### Why the dispatch caches moved from static to per-instance (4.2.0)

Before 4.2.0, `Mapper.EntryPointCache` was `static`/global and safe to share across every `IMapperConfig` instance *only* because the cached wrapper carried no config-specific state — it re-resolved `config.GetMap<TSource,TDestination>()` fresh from whichever `config` was passed at each call. That re-resolution was itself a dictionary lookup, paid on every single `Map` call in addition to the `EntryPointCache` lookup that found the wrapper in the first place. Moving `_entryPoints` (and the new `_listMappers`) to instance fields on `Mapper` removes that redundant lookup entirely: a `Mapper` wraps exactly one `IMapperConfig` for its whole lifetime, so its cache can safely hold the *already-resolved* builder reference (not just a way to re-look-it-up), with zero risk of cross-config contamination — two `Mapper` instances over two different configs simply have two separate, never-shared dictionaries. This does mean two different `Mapper` instances wrapping the *same* config each pay their own cache-miss cost independently (a `Mapper` is meant to be built once and reused, e.g. as a DI singleton — see `AddAutoMapperLite` above); it does not mean two different configs can share a cache entry, which was never possible either way. The reflection-metadata caches (`PublicPropertiesCache`, `PropertiesByNameCache`) are unaffected and remain `static`/global, since `Type → PropertyInfo[]` is a process-wide invariant with no config axis at all.

### Why `MapBuilder.GetCompiledMap` checks the field directly instead of always calling `LazyInitializer.EnsureInitialized` (4.3.0)

`GetCompiledMap` used to be exactly `LazyInitializer.EnsureInitialized(ref _compiledMap, () => MappingPlanCompiler.Compile(this, config))`, written directly in the method body. This looks like ordinary double-checked lazy initialization, but has a subtle, expensive flaw: the lambda `() => MappingPlanCompiler.Compile(this, config)` captures `this` and `config`, so C# must allocate a *new closure object and a new delegate wrapping it* at the call site every time this line executes — regardless of whether `EnsureInitialized` goes on to actually invoke it. `EnsureInitialized` only *runs* the factory once, but the C# compiler has no way to avoid *constructing* the `Func<T>` argument before passing it in; that construction is unconditional. Every single call to `GetCompiledMap` — which is to say, every single `Map` call through every dispatch path, and every same-name nested single-object property assignment via `BuildNestedObjectAssignment`'s baked-in `builder.Map(...)` call — paid for one throwaway closure + delegate allocation, even in the overwhelmingly common case where `_compiledMap` was already set and the factory was never going to run. This was the single largest source of AutoMapperLite's excess allocation versus Manual/Mapster in every scenario touching a nested property or a collection (see the CHANGELOG 4.3.0 entry for the measured before/after). The fix is to check `_compiledMap` directly first (via `Volatile.Read`, since the field isn't `volatile`-qualified and a plain read wouldn't be guaranteed to observe another thread's publish) and only fall through to a *separate* method containing the lambda — `CompileAndCache` — on the rare cold path. If you add another `LazyInitializer.EnsureInitialized`/similar lazy-init call anywhere on a path that runs more than once per cached value's lifetime, write it this same way (fast-path field check first, lambda-allocating slow path in its own rarely-called method), not inline.

### Why nested/list dispatch delegates are resolved once *per cache entry*, never eagerly at another type's plan-compile time (4.3.0 constraint)

4.3.0 made `Mapper.BuildEntryPoint`, `Mapper.BuildListMapper`, and `MappingPlanCompiler.MapListWithBuilder` all call `builder.GetCompiledMap(config)` **once** (caching the raw delegate) instead of calling `builder.Map(item, config)` **per item/per call** — this is safe and was the fix described above, extended to loops. It would *not* be safe to take this one step further and have `MappingPlanCompiler.BuildNestedObjectAssignment`/`BuildNestedListAssignment` do the same thing — i.e., call `GetCompiledMap` on the *nested* builder eagerly, at the *parent's* plan-compile time, and bake the resulting delegate into the parent's expression as a constant instead of baking in the builder + a runtime `builder.Map(...)` call. That would break self-referential types: if `Employee.Manager` is itself typed `Employee` (same-name, registered map), compiling `Employee`'s plan would need to fully compile `Employee`'s plan again *before returning*, recursing infinitely at configuration time and `StackOverflowException`-ing on the very first `Map` call — for *any* data, even a chain of two acyclic objects, not just genuinely circular references. The three places that *were* changed are all safe because they're only ever invoked in response to an actual pending `Map` call already in progress for *that exact type pair* (never from inside another type's plan being compiled), so resolving that one type pair's own compiled delegate there is no earlier than it would have happened anyway. `MapperTests.Map_HandlesSelfReferentialType_WithAcyclicData` (using `EmployeeNode`/`EmployeeNodeDto` in `TestModels.cs`) pins this down — if you're tempted to "optimize away" the remaining `builder.Map(...)` call in `BuildNestedObjectAssignment`/`BuildNestedListAssignment`, run that test first and understand why it would fail before touching it.

### Documented behavior: `List<T>` mapping dispatches by declared item type, not each element's runtime type

`Map<List<TDestination>>(object source)` (and the equivalent nested-property path) resolves the item map from the *source collection's own* `Type` — e.g. `List<TSourceItem>`'s generic argument — once per call, not from each element's individual runtime type. A `List<Animal>` containing a `Dog` instance therefore maps every element, including the `Dog`, through `Animal`'s registered map; `Dog`'s own extra properties are simply not part of that map, the same as if the list had been declared and consumed as `List<Animal>` anywhere else in C#. No `Dog`-specific map is required. This only differs from pre-4.2.0 behavior in one respect: previously, a `List<Animal>` containing `Dog` instances with **only** `CreateMap<Animal, AnimalDto>()` registered (no map for `(Dog, AnimalDto)`) would throw for every `Dog` element, since dispatch used `item.GetType()`; it now succeeds, using `Animal`'s map for every element. See `MapperTests.Map_MapsHeterogeneousList_UsingDeclaredItemTypesMap_NotEachItemsRuntimeType`. Source collections whose item type can't be determined from their own `Type` (non-generic `IEnumerable`) still dispatch per element by runtime type via `MapListByRuntimeType`, unchanged.

### Disclosed behavior change: exceptions no longer arrive wrapped in `TargetInvocationException`

Before the original compiled-plan redesign, `Mapper.Map<TDestination>` dispatched through `MethodInfo.Invoke`, so any exception thrown deep in the mapping logic (missing map, bad `ForMember` return value, missing parameterless constructor) arrived wrapped in a `System.Reflection.TargetInvocationException`. The compiled-plan architecture removed reflection `Invoke` from the entire call chain, so these exceptions propagate **directly** as `InvalidOperationException` instead. This was never a documented part of the public contract (it was a leak of the old implementation), so it isn't treated as a breaking API change, but it *is* an observable behavior change. The 4.2.0 dispatch redesign reintroduced a reflective `Invoke` at the entry-point-cache-miss path (`GetOrBuildEntryPoint`/`GetOrBuildListMapper`, via `InvokeBuilder`) — a missing registration can now throw *during* that `Invoke` call; `InvokeBuilder` explicitly unwraps `TargetInvocationException` via `ExceptionDispatchInfo` so this disclosed behavior stays true. If you add another `MakeGenericMethod(...).Invoke(...)` call anywhere on a path that can throw a "real" mapping exception, route it through `InvokeBuilder` (or an equivalent unwrap) too.

## Key constraints to preserve when modifying

- Target frameworks are `net6.0;net7.0;net8.0;net9.0;net10.0` with nullable reference types and implicit usings enabled. `Microsoft.Extensions.DependencyInjection.Abstractions` is kept at the latest version (`10.0.11` as of this writing) per explicit instruction to never downgrade packages; it declares (and would otherwise warn on) "not tested" support for net6.0/net7.0, which is suppressed via `SuppressTfmSupportBuildWarnings` in `AutoMapperLite.csproj` — verified benign by an actual runtime smoke test (DI container built, `AddAutoMapperLite` resolved, a real `Map<T>` call executed) on net6.0, not just assumed from the warning text.
- Packing requires `dotnet pack -c Release`, not `dotnet build` (see the note under Commands above) — bump `Version` in `AutoMapperLite.csproj` (and update `PackageReleaseNotes`) when shipping a change intended for release.
- Public API surface (`IMapper`, `IMapperConfig`, `MapBuilder<,>`, `Profile`) is what consuming projects bind against directly; changes here are breaking changes for NuGet consumers (and, for interface additions like the 4.2.0 `Map<TSource, TDestination>` overload, technically breaking for anyone who implements `IMapper` themselves — additive for everyone who only *calls* it, which is the overwhelming majority of consumers). `IMapper.Map<TDestination>`'s `source` parameter is `object?` (not `object`) — this is intentionally nullable since the method has always accepted and handled `null` at runtime.
- `MapBuilder<,>.MemberMappings` is `internal`; `AutoMapperLite.csproj` grants `AutoMapperLite.Tests` access via `InternalsVisibleTo` so tests can assert on registered mapping keys directly.
- The compiled plan applies *every* `MemberMappings` key prefixed with a given top-level destination property to the same nested instance (see `AutoMapperLite.Tests/MapperTests.cs::Map_UsesForPath_ForDeeplyNestedDestination`), so multiple `ForPath` calls under the same top-level property all take effect. Preserve this when touching `BuildNestedAssignment` in `Core/MappingPlanCompiler.cs`.
- The reflection-metadata caches in `Core/Mapper.cs` — `PublicPropertiesCache`/`PropertiesByNameCache` — are `static` and process-wide by design (`Type` → metadata is a process-wide invariant). The **dispatch caches** (`_entryPoints`, `_listMappers`) are the opposite: **instance fields, deliberately not static** — see "Why the dispatch caches moved from static to per-instance" above. Don't merge these two categories; they have opposite correct scopes for opposite reasons. The *compiled plan itself* is a third category again: it's config-specific and lives on `MapBuilder`, not `Mapper` — see "Why the plan lives on `MapBuilder`" above.
- `AutoMapperLite.Benchmarks/MappingBenchmarks.cs`'s `ComparisonBenchmarkBase.Setup()` builds **one** `Mapper` instance and captures it in every `ForMember` closure (`var mapper = new Mapper(config); ...ForMember(..., src => mapper.Map<...>(...))`). Do not change this back to `new Mapper(config)` *inside* a `ForMember` lambda — that pattern (present in an earlier version of this benchmark) allocates a fresh `Mapper` per nested call, meaning its per-instance entry-point cache never warms up, and was quietly inflating the Nested/DeepNested benchmark numbers before the 4.2.0 dispatch redesign. The tests (`MapperTests.cs`) still use the `new Mapper(config)`-inside-the-lambda form in a couple of illustrative one-shot correctness tests — that's fine there (it's not a hot loop), just don't copy that specific pattern into anything performance-sensitive.
- A source item that is `null` inside a collection passed to `Map<List<TDestination>>` will `NullReferenceException` on `item.GetType()` — this is a pre-existing limitation, not something recently introduced; treat it as a known edge case rather than "fixing" it silently if you touch that loop, since there's no single obviously-correct behavior for a null list element (skip it? add `null` to the result? both are behavior changes).
- `ForMember`/`ForPath` functions must return the *already-mapped* value, not the raw source sub-object — the library never implicitly converts types inside a custom mapping function. When source/destination property types differ, the function has to call back into a `Mapper` itself (e.g. `src => mapper.Map<CountryViewModel>(src.Country)`, capturing a `Mapper` built from the same `config` in the closure). The README's flagship "Create Mapping Profiles" example previously got this wrong (passed the raw `Country` straight through) and threw `InvalidOperationException` at runtime for *anyone who copy-pasted it* — verified by actually running it, not just by reading the code. If you touch that example again, re-run it, don't just eyeball it.
- **A `null` source property value is skipped, not assigned** — the compiled auto-map assignment for a nullable/reference-typed source property is wrapped in `Expression.IfThen(NotEqual(source, null), assign)` (see `BuildAutoMapAssignment` in `Core/MappingPlanCompiler.cs`), so a destination's own default (field initializer, etc.) is preserved rather than overwritten with `null`. This is easy to miss because a same-typed round trip can't distinguish "skipped" from "assigned null" (both look like null); `MapperTests.Map_SkipsAssignment_WhenSourcePropertyIsNull` uses a destination with a *non-null* default specifically to make the distinction observable. This differs from AutoMapper's default (which does overwrite with null) — worth calling out if anyone asks why a null source field didn't clobber a computed default.
- **Auto-map only fires on an exact `Type` match** (or a registered map). Two *different* enum types with identical member names, `enum → string`, and numeric widening (`int → long`, etc.) are all silently left at the destination's default — not converted, not thrown. This is a deliberate scope boundary (no convention/coercion engine, consistent with the "lightweight, not AutoMapper" positioning — see `docs/comparison.html`), not a bug; don't "fix" it by quietly adding conversion logic without discussing the API/behavior change first. This check is evaluated once, at plan-build time (`config.HasMap(...)` inside `BuildAutoMapAssignment`), not per call.
- **Destination types need a public parameterless constructor** — instances are created via `Expression.New(Type)` (see `CreateInstanceExpression` in `MappingPlanCompiler`). Positional records (`record Foo(int A)`) and any class requiring constructor arguments throw a clear `InvalidOperationException` naming the type. Records *with* a parameterless constructor and `{ get; init; }` properties work fine — a compiled property assignment can set an init accessor even though the C# compiler wouldn't let you call it directly outside the constructor (the `init` restriction is compile-time only). No constructor-parameter mapping is implemented. **Value types (structs) are handled by `Expression.New(Type)` even without an explicitly-declared parameterless constructor** — do not "fix" this by switching to `type.GetConstructor(Type.EmptyTypes)`, which returns `null` for such structs and was a real regression caught by `MapperTests.Map_PopulatesValueTypeDestination` during this redesign.
- **Circular/self-referencing object graphs are not supported and will `StackOverflowException`** (an uncatchable, process-terminating crash — not an `InvalidOperationException` like the other failure modes above). If `A` has a same-name/registered-map property of type `B`, and `B` has a same-name/registered-map property back to type `A`, mapping an instance where that reference cycle is real (e.g. `a.B.A == a`, a common shape for untracked EF Core navigation properties) recurses through the compiled nested-mapping call chain forever. This is a deliberate scope boundary, not a bug to silently fix: AutoMapper's equivalent (`PreserveReferences`) requires a per-call reference-tracking context (e.g. a `Dictionary<object, object>` allocated on every single `Map` call) that would add allocation to the hot path for every consumer to protect the minority mapping genuinely cyclic graphs — directly contradicting this library's "minimal warm-path allocation" goal. Don't add one without an explicit decision to trade that off; and don't add a unit test that maps a genuinely cyclic instance, either — the resulting stack overflow can't be caught by `try`/`catch` and will crash the whole test-runner process, not just fail one test.
